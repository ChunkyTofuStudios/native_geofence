native_geofence lifecycle

A geofence registration lives in the operating system, never in a Flutter engine. Every event runs in a background engine whose isolate starts at callbackDispatcher, never in the UI engine, and that isolate shares no Dart memory with the UI, even when the app is open.     What exists right now

    The mental model

    The facts that explain almost every scenario above. If a change breaks one of these, expect lifecycle bugs.

    • Registrations live in the OS. iOS keeps regions in Core Location's monitoredRegions across termination and, in practice, reboot. Play services forgets Android geofences on reboot, app update, force stop, reinstall, app or Play services data clear, and GEOFENCE_NOT_AVAILABLE. Only reboot is handled automatically: a BOOT_COMPLETED receiver replays the plugin's SharedPreferences cache. After the other cases the app must call reCreateAfterReboot() itself (a reinstall or app data clear normally wipes the cache too), and GEOFENCE_NOT_AVAILABLE is not reconciled at a1ca8f9 (see the deviations).
    • Callbacks never run in the UI isolate. Even with the app open, each event runs in a background engine whose root isolate starts at callbackDispatcher. main() never runs there, and no Dart memory is shared with the UI isolate.
    • One engine per burst, or one per event. iOS keeps one headless engine alive while events are queued and destroys it when the queue is empty and no callback is in flight. Android builds a new FlutterEngine for every WorkManager job.
    • Native code serializes callbacks. iOS uses an in-memory eventQueue with one awaitedCallbackId. Android uses the unique WorkManager chain geofence_callback_work_group with APPEND. Events raised inside a callback, such as a nested geofence's initial trigger, run after it.
    • The boot handshake is ordered. Native registers NativeGeofenceBackgroundApi, Dart registers the geofenceTriggered handler and calls triggerApiInitialized, native sends geofenceTriggered, and Dart replies only after the user's Future completes.
    • NativeGeofenceApi is on every engine. That is why NativeGeofenceManager works inside callbacks. NativeGeofenceBackgroundApi and the trigger handler exist only on background engines.
    • Everything shares the main thread. Since Flutter 3.29 merged the UI and platform threads, Core Location delegate calls, broadcast receivers, startWork, Pigeon handlers and every engine's root isolate run on the same thread. Heavy synchronous work in a callback janks the UI.
    • The OS owns the clock. iOS gives a short wake window that is not guaranteed: around 10 s in Apple's archived guide, and per Apple DTS anything from suspension as soon as the waking callback returns up to about 30 s. The intended design holds a background task from enqueue until cleanup (the code at a1ca8f9 takes none; see the deviations). The plugin's 60 s rule only unblocks the queue. Android stops a job after 10 minutes (an expedited job with little quota left is only guaranteed 1 minute), then WorkManager runs it again.
    • Handles resolve by name. initialize() stores the callbackDispatcher handle and createGeofence stores one handle per geofence. Both resolve through Flutter's on-disk callback cache by function name and library, so renaming or moving a callback breaks delivery until it is registered again.
    • Promotion is Android only, and separate from the worker. promoteToForeground() starts NativeGeofenceForegroundService with a 5-minute wake lock. The engine stays in the worker; the service only raises the process's priority. On iOS both calls are logged no-ops.

    Invariants to preserve

    Rules the current design depends on. Numbers are for reference in reviews.

    1. iOS: one CLLocationManager and one delegate per process, both in LocationManagerDelegate.shared. A delegate per engine replaces the manager's weak delegate and dies with its engine (the 1.1.0 regression); a second manager delivers every event twice.
    2. iOS: LocationManagerDelegate.shared is first touched on the main thread inside application(_:didFinishLaunchingWithOptions:), through setPluginRegistrantCallback. On a background launch without a UI scene it is the only plugin code that runs before the event, and Core Location calls back on the creating thread's run loop.
    3. iOS: setPluginRegistrantCallback runs before any engine registers the plugin, or register(with:) calls fatalError.
    4. Callbacks never run on the UI engine. It never gets NativeGeofenceBackgroundApi or a geofenceTriggered handler, and NativeGeofenceBackgroundManager is valid only inside callbacks.
    5. NativeGeofenceApi exists on every background engine, so nested calls work. On iOS that depends on the app's registrant closure including the plugin; on Android, on FlutterEngine(context) auto-registration.
    6. The handshake keeps its order with no async hop. Native sets up NativeGeofenceBackgroundApi before Dart can send anything; Dart initializes the binding, registers the trigger handler and assigns NativeGeofenceBackgroundManager before triggerApiInitialized; native sends geofenceTriggered only after it, so the message is never dropped.
    7. Native code never blocks the main thread waiting for Dart. Nested Pigeon calls must be served while a callback's Future is pending.
    8. The engine outlives the user's Future. Reply only after await callback(...); iOS tears down only when the queue is empty and callbacksInFlight == 0; a destroyed engine is never reused. The only exceptions are forced by the OS: WorkManager stopping an Android job (onStopped then destroys the engine mid-callback) and the process being killed.
    9. Serialization is native. At most one awaited callback (iOS) or one running worker (Android). Events raised by a callback are delivered after it, never dropped. Nothing may cancel the unique work chain or replace it while work is pending. APPEND_OR_REPLACE is allowed: it starts a new chain only when the existing one already failed or was cancelled.
    10. iOS: at most one headless engine at a time, and nativeGeofenceBackgroundApi != nil means a live, running engine.
    11. iOS createGeofence persists the handle and the awaiting flag before startMonitoring, because didDetermineState can arrive immediately.
    12. callbackDispatcher keeps its name and library (package:native_geofence/src/callback_dispatcher.dart) and its @pragma('vm:entry-point'). Installed apps hold persisted handles that resolve by name.
    13. Persisted data stays readable by newer plugin versions. UserDefaults, SharedPreferences and WorkManager's database survive app updates, so their keys, including the worker's input-data key, keep their names. Android's persistent_geofence/<id> JSON and worker payloads are decoded with the default kotlinx Json, which rejects unknown keys and requires every property without a default: add fields only with defaults (as triggerTimestampMillis was), and keep the names of stored enum cases such as GeofenceEvent. An undecodable payload loses its event (at a1ca8f9 its Result.failure() also fails every event appended behind it; see the deviations). An undecodable cache entry is skipped by getGeofences and reCreateAfterReboot and leaves the receiver unable to resolve that geofence's callback, though getGeofenceIds still lists its id.
    14. NativeGeofenceErrorCode is append-only. Android sends the raw enum index as the error code.
    15. No messageChannelSuffix. The calling isolate's messenger selects the engine; do not add shared global channels.
    16. All plugin native code stays on the main thread. Correctness relies on that, not on objc_sync or the Kotlin lock. Android's onStopped may only post to the main looper.
    17. Android: one explicit, mutable geofence PendingIntent. Play services fills in its extras and caps an app at 5 PendingIntents. Resolve each geofence's callback by its id, never from the PendingIntent's extras.
    18. Android: startForeground stays in NativeGeofenceForegroundService.onCreate, before any slow work, to meet the start deadline.
    19. Android: the foreground service exists only between one callback's promote and demote, and the worker's end paths stop it.
